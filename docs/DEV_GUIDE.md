>
> 📁 **Связанные документы:**
> * [CLAUDE.md](../CLAUDE.md) — краткая шпаргалка для AI-ассистента (команды, архитектура, ловушки).

> * [REVIEW_GUIDE.md](REVIEW_GUIDE.md) — регламент конструктивного код-ревью, чек-листы по компонентам и план комплексного ревью всего проекта.

## 1. Главные правила и инварианты

### 1.1. Обязательное регулярное обновление `ROADMAP.md` и `TASKS.md` ⚠️
* При начале любой задачи из [ROADMAP.md](ROADMAP.md) или [TASKS.md](TASKS.md) **обязательно переключай статус этапа/подзадачи** в актуальное состояние (`В процессе` / `Выполнено`).
* По завершении этапа или подзадачи:
  1. Отмечай чекбоксы `[x]`;
  2. Заполняй раздел «Лог изменений этапа» (какие файлы созданы, изменены, какие тесты пройдены);
  3. Если в процессе работы вскрылись технические нюансы или потребовались уточнения — дополняй соответствующий блок в [ROADMAP.md](ROADMAP.md) и [TASKS.md](TASKS.md).

### 1.2. Обязательное саммари перед пушем кода (Pre-Push Summary) 📢
* **Никогда не пушить код в удаленный репозиторий без явного одобрения пользователя.**
* Перед тем как пользователь примет решение о коммите и пуше (`git push`), AI **обязан предоставить структурированное саммари** по разработке, включающее:
  1. **Что сделано:** краткий и четкий перечень реализованных фич, исправлений или рефакторинга;
  2. **Список затранутых файлов:** таблица или список созданных/модифицированных файлов с описанием их роли;
  3. **Статус верификации:** результаты запуска автотестов (`npm test`), подтверждение отсутствия регрессий в оффлайн-режиме и корректности отображения тем (Dark/Light);
  4. **Состояние ROADMAP & TASKS:** ссылка на обновленный статус в [ROADMAP.md](ROADMAP.md) и [TASKS.md](TASKS.md);
  5. **Дальнейшие шаги:** что рекомендуется делать на следующем этапе.

### 1.3. Сохранение оффлайн-режима («Двойной режим»)
* Онлайн-функционал **не должен** ломать оффлайн-игру за одним экраном.
* Стартовое меню обязано предоставлять выбор:
  * 🏠 **«Локальная игра»** (классический оффлайн Quiz U за одним ПК/ноутбуком);
  * 🌐 **«Сетевая комната (Хост)»** (сетевой режим со смартфонами).

### 1.4. Соответствие код-стайлу проекта
* **Zero-Build для Web:** В клиентской части (`index.html`, `js/`, `css/`, `mobile/`) запрещены веб-бандлеры (Webpack, Vite). Чистый HTML5, CSS3, ES6+ JavaScript.
* **Изолированный бэкенд:** Код сервера комнат живет исключительно в папке `server/` со своим `server/package.json`.
* **Обязательные две темы:** Любые новые экраны, элементы управления и модальные окна поддерживают тёмную (дефолт) и светлую тему (`body.light-theme`).
* **Относительные пути:** Только `/` (например: `assets/music/track.mp3`). Никаких абсолютных путей ОС.
* **Тестирование:** `npm test` (`node --test tests/**/*.test.js`) должен проходить без ошибок после каждого изменения.

> [!IMPORTANT]
> На Windows (PowerShell) запускать серверные тесты отдельно:
> ```powershell
> cd server
> npm.cmd test
> cd ..
> ```
> Оба набора тестов обязательны перед каждым коммитом:
> **264 клиентских** (`npm test` в корне) + **52 серверных** (`npm test` в `server/`).

### 1.5. Строгая модель ветвления: ЗАПРЕТ на слияния в `main` и `dev` 🌿🚫
* **`main` и `dev` ЗАМОРОЖЕНЫ:** В ветки `main` и `dev` изменения сетевого мультиплеера **НЕ вливаются**! Они остаются нетронутыми для классической оффлайн-версии игры.
* **Базовая ветка для всей сетевой разработки — `feature/online-multiplayer`:**
  - Любые фичи и этапы сетевого режима разрабатываются в ветках, отпочкованных **строго от `feature/online-multiplayer`** (например: `feature/online-multiplayer/host-lobby`, `feature/online-multiplayer/mobile-client`).
  - Все готовые и протестированные фичи вливаются **строго обратно в `feature/online-multiplayer`**.
  - **Категорически запрещено** выполнять слияние сетевых веток в `dev` или `main`.

### 1.6. Регламент конструктивного код-ревью (Code Review) 🧐
* Любые изменения перед слиянием в базовую ветку подлежат обязательному код-ревью в соответствии со стандартами [REVIEW_GUIDE.md](REVIEW_GUIDE.md).
* **Принцип конструктивности:** критика относится исключительно к коду, а не к автору; замечания сопровождаются обоснованием («почему?») и готовым примером кода.
* **Стандарт Conventional Comments:** использование префиксов `[blocker]`, `[should]`, `[suggestion]`, `[nit]`, `[question]`, `[praise]`.
* **Запрет мержа с блокерами:** наличие неразрешённых замечаний с префиксом `[blocker]` делает слияние невозможным.
* **Pull Request Template:** оформление запросов на слияние строго по шаблону `.github/pull_request_template.md`.

## 3. Сетевой протокол и античит

1. **Формат сообщений:**
   ```json
   {
     "type": "MESSAGE_TYPE",
     "roomId": "ABCD",
     "senderId": "uuid",
     "payload": { ... }
   }
   ```
2. **Античит (Сокрытие ответов):**
   * Клиентам игроков поле `question.a` (правильный ответ) и `question.a_img` **никогда не отправляется** до завершения раунда ответа ведущим.
   * Игрок видит только: текст вопроса, тип, стоимость, медиа и лимит времени.
3. **Валидация таймингов:**
   * Сервер — единственный источник времени. Если событие `BUZZ_PRESS` или `ANSWER_SUBMIT` пришло после истечения таймера на сервере, оно отклоняется с кодом `TIMEOUT`.

## 4. Git Workflow и модель ветвления 🌿

1. **Базовая ветка сетевой разработки:**
   * Вся разработка мультиплеера ведётся исключительно в базовой ветке **`feature/online-multiplayer`**.
   * Ветки `main` и `dev` **заморожены** и не принимают сетевые коммиты.
2. **Ветвление под каждую фичу/этап:**
   * Для каждого этапа создаётся отдельная ветка от базовой:
     * `git checkout feature/online-multiplayer`
     * `git checkout -b feature/online-multiplayer/<feature-name>` (например: `feature/online-multiplayer/host-lobby`, `feature/online-multiplayer/mobile-client`).
3. **Слияние фич в базовую ветку:**
   * После реализации фичи и успешного прохождения всех тестов (`npm test`), подветка фичи вливается **строго обратно в `feature/online-multiplayer`**:
     * `git checkout feature/online-multiplayer`
     * `git merge feature/online-multiplayer/<feature-name> --no-ff`
4. **Атомарные коммиты:**
   * Каждому логическому блоку изменений — отдельный коммит:
     * `feat(core): extract GameStateMachine logic`
     * `feat(server): implement room lifecycle and buzz arbitration`
     * `feat(host): implement host online lobby and QR code`
     * `docs: update ROADMAP.md progress for stage 3`
5. **Процедура перед пушем:**
   * Шаг 1: Успешный прогон `npm test` и `cd server && npm test`.
   * Шаг 2: Обновление чекбоксов и лога в [ROADMAP.md](ROADMAP.md) и [TASKS.md](TASKS.md).
   * Шаг 3: **Проведение Self-Review и прохождение ревью** согласно [REVIEW_GUIDE.md](REVIEW_GUIDE.md).
   * Шаг 4: **Формирование и вывод саммари пользователю** (согласно п. 1.2).
   * Шаг 5: Ожидание подтверждения пользователя перед выполнением `git push`.
6. **Чистота репозитория:** Запрещено коммитить `node_modules`, временные дампы, файлы логов и IDE-кэш.
