# Code Style & Architecture Rules — Quiz U («Город Ю»)

Эти правила обязательны к исполнению при разработке, рефакторинге и добавлении нового функционала в проект.

---

## 1. Архитектурные принципы и стек

- **Zero-Build & Vanilla Stack**:
  - Стек проекта: чистый HTML5, CSS3 и ванильный JavaScript (ES6+).
  - Никаких бандлеров (Webpack, Vite, Rollup) и компиляторов (Babel, TypeScript).
  - Никаких внешних runtime-фреймворков и библиотек (React, Vue, jQuery, Lodash и др.) без прямого и явного указания пользователя.
- **Автономность и переносимость**:
  - Приложение должно работать как при запуске через локальный веб-сервер (`http://localhost:...`), так и при открытии `index.html` локально.
  - Все пути к ресурсам — только относительные, со стандартными прямыми слэшами `/` (например, `assets/music/track.mp3`). Никаких абсолютных путей операционной системы (`C:\...`).

## 2. JavaScript (ES6+)

### 2.1. Объявление переменных и чистота кода
- Использовать `const` по умолчанию. Если переменная действительно переприсваивается — использовать `let`.
- Использование `var` **запрещено**.
- Использовать строгие сравнения (`===`, `!==`).
- Использовать современные возможности языка: деструктуризацию, spread-оператор, опциональные цепочки (`?.`), оператор нулевого слияния (`??`), шаблонные строки.

### 2.2. Защитное программирование (Defensive DOM)
- Любое обращение к элементам DOM должно быть безопасным:
  ```js
  // Правильно:
  const button = document.getElementById('my-btn');
  if (button) {
    button.addEventListener('click', handleClick);
  }
  ```
- Не полагаться на безусловное существование узлов, особенно при смене экранов/модалок.
- Очищать интервалы и таймауты (`clearTimeout`, `clearInterval`) перед созданием новых или при размонтировании экранов.
- Для предотвращения двойных кликов и race conditions в анимациях и модальных окнах использовать флаги состояния (например, `isDismissing...`, `isLoading...`).

### 2.3. Web Audio API и медиа
- Инициализировать `AudioContext` лениво (по первому клику/действию пользователя) во избежание блокировки браузером (Autoplay Policy).
- Обязательно проверять `audioCtx.state === 'suspended'` и вызывать `audioCtx.resume()`.
- Воспроизведение звуков и генерацию осцилляторов оборачивать в `try { ... } catch (e) { ... }`, чтобы сбои аудио не ломали игровой процесс.

### 2.4. Работа с LocalStorage
- Любое чтение (`localStorage.getItem`) и запись (`localStorage.setItem`), а также `JSON.parse` оборачивать в блок `try/catch`.
- Всегда задавать безопасные дефолтные значения на случай поврежденных данных или приватного режима браузера.

### 2.5. Разделение логики и представления
- Чистая бизнес-логика (расчет очков, нормализация структур паков, проверка победителя, логика таймеров и фильтрации) должна быть вынесена в чистые/изолированные функции.
- Это гарантирует возможность модульного тестирования без браузерного окружения.

## 3. CSS и оформление

### 3.1. Темы оформления (Обязательно!)
- Проект поддерживает две темы: **тёмную** (по умолчанию) и **светлую** (`body.light-theme`).
- **Каждый** новый компонент, модальное окно или кнопка обязаны корректно отображаться в обеих темах:
  - Использовать существующие CSS-переменные темы (`var(--bg-...)`, `var(--text-...)`, `var(--accent-...)` и т.д.).
  - При необходимости явно прописывать стили для `.light-theme .my-component`.
- Контрастность текста и читаемость на фонах должны сохраняться в обоих режимах.

### 3.2. Именование и структура стилей
- Использовать `kebab-case` для классов (например, `modal-backdrop`, `round-card__header`).
- Стили викторины — в `css/style.css`, стили каталога и фильтров — в `css/catalog.css`.
- Для анимаций отдавать предпочтение свойствам `transform` и `opacity` (аппаратное ускорение, отсутствие reflow).

### 3.3. Векторная графика (SVG)
- Для уникальных анимаций, спец-вопросов («Кот в мешке», «Аукцион») и иллюстраций использовать встроенные inline-SVG или генераторы SVG-разметки с градиентами и тенями.

## 4. Данные паков и медиа-ресурсы

- Все файлы пакетов вопросов (`паки вопросов/**/*.json`) должны быть валидным JSON в кодировке UTF-8.
- Структура пакета должна соответствовать схеме: `rounds -> themes -> questions`.
- Поля вопросов: `q` (вопрос), `a` (ответ), `cost` (стоимость), опционально `type` (`cat`, `auction`, `video`, `music` и т.д.).
- Медиафайлы раскладываются строго по предназначенным директориям:
  - `assets/music/` — аудио (MP3);
  - `assets/video/` — видео (MP4);
  - `assets/q_img/` — изображения к вопросам;
  - `assets/a_img/` — изображения к ответам.

## 5. Тестирование и контроль качества

- Тесты пишутся с использованием встроенного тест-раннера Node.js (`node:test` + `node:assert`).
- Запуск тестов: `npm test` (или `node --test tests/**/*.test.js`).
- Любые изменения в механике игры, расчете очков, переключении ходов или структуре каталога должны сопровождаться проверкой существующих тестов и добавлением новых тест-кейсов в `tests/`.
- Не допускать поломки имеющихся тестов при рефакторинге.

---

## 6. Процесс разработки (Git Workflow)

- Основная ветка для разработки и правок — **`feature/online-multiplayer`** (для сетевого режима) или `dev` (для базового оффлайна).
- Коммиты должны быть атомарными, с понятными описаниями внесенных изменений на русском или английском языке.
- Язык интерфейса приложения — русский.

---

## 7. Конструктивное код-ревью (Code Review)

- Все изменения перед слиянием подлежат проверке по правилам [REVIEW_GUIDE.md](docs/REVIEW_GUIDE.md).
- Комментарии и фидбек формулируются строго по стандарту Conventional Comments (`[blocker]`, `[should]`, `[suggestion]`, `[nit]`, `[question]`, `[praise]`).
- Критика направлена исключительно на код, а не на автора.
- Любое замечание должно содержать контекст, обоснование риска («почему это важно») и конкретный пример кода или исправления.
- Запрещено выполнять слияние при наличии неразрешённых замечаний с префиксом `[blocker]`.
